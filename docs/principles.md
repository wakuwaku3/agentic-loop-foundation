# Agentic Loop 大原則

更新日: 2026-08-22

以下は `AGENTS.md` から毎回参照されても、ループの判断を具体的に拘束できる情報量を保つ。
実装手順や調整値は含めないが、方式を変えても失ってはならない保証は省略しない。

## 大原則

### 1. 人間がループを統制する

- ループの自律性は人間の統制を越えない。人間は全体、repository、Requirement単位で開始、停止、再開、取消できる。
- 停止指示後は新しい副作用を開始しない。command受付だけでなく、対象process、lease、権限および残存副作用を確認して停止完了を判定する。
- 到達不能なrunnerが残っても、失効した権限による変更、状態更新、Stable昇格を確定させない。
- 破壊的、不可逆、または人間が定めた費用・権限の上限を越える判断だけは、実行前に明示的な承認を得る。通常の調査、変更、検証、昇格に人間reviewを要求しない。

### 2. Applicationで要求が成立するまでループする

- 最終成果物はPRや作業記録ではなく、継続的に改善されるApplicationである。
- 人間が伝えるHowを確定要件とせず、その背景にある課題を深掘りし、価値、緊急性、risk、cost、依存を踏まえてアプローチと優先順位を判断する。
- 作業、変更、PR、test成功を完了とはみなさない。要求と不変条件がPreviewで実証され、Stableへ昇格したことをシステム上の完了とする。
- 大きなRequirementは安全に統合できる増分へ分解し、複数の変更を通じて元のRequirementを追跡する。RequirementとPRを1対1に固定しない。
- 満たせない要求を黙って縮小したり、検証できない結果を成功として報告したりしない。

### 3. 問題解決能力と復旧手段を維持する

- Applicationとループ自身の変更はPreviewで実運用し、定義済みの条件を満たしてからStableへ昇格する。
- Stable候補の全ユーザー向け機能をPreview実環境で確認する。外部systemやAI Providerに依存する機能は、対象となる実物との接続を代替せずに確認する。
- StableとPreviewは同じcanonical stateを共有してよいが、共存中の状態、lease、停止、checkpoint、副作用の契約を互換に保つ。
- Previewが壊れてもStableを独立して起動し、同じRequirementを安全に再開できるようにする。
- 変更は可能な限り新しいmodule/versionの追加、明示的な切替、旧版の保持、不要後の削除として行い、切り戻しと影響範囲の限定を可能にする。
- ループ自身を更新するときも、更新対象から独立した既知のStable版または管理経路を残し、自己更新の失敗で停止・復旧能力を同時に失わない。
- 副作用は重複確定を防ぎ、中断後は記憶ではなくcanonical stateと観測した外部状態から再開する。

### 4. 秘密、権限、所有権を守る

- 秘密情報をrepository、Requirement、成果物、状態、prompt、logへ保存または公開しない。
- credentialは実行時に認可されたsecret storeから必要なprocessへだけ渡し、canonical stateやprovider間のhandoff情報へ含めない。
- 出力と外部送信を秘密漏洩について検査・redactし、漏洩または漏洩の疑いがあれば使用を停止してcredentialを失効・交換できるようにする。
- componentとworkerには、対象repository、役割、期間に必要な最小権限だけを与え、権限を推測せず副作用の前に検証する。
- control planeとcanonical stateは利用者自身がself-hostでき、既定ではsingle-tenantとする。他利用者の要求、credential、計算資源、費用を無断で同居・共有しない。
- 利用者のbacklogを一つに保ちながら、repositoryごとの権限、作業空間、状態、成果を分離する。worker資源を共有してもrepository間で混同しない。

### 5. 費用と有限資源を制御する

- 人間が許容していない金銭的コストを発生させない。budget通知だけを強制停止手段とみなさず、利用量を実際に制限する。
- AI、compute、storage、network、外部API、worker、入力規模に明示的な上限と停止条件を持つ。
- 無限poll、無限retry、無期限lease、無制限のlog・履歴保存を行わない。
- AI provider枠とrunner slotは共有有限資源として、課題の価値、緊急性、risk、cost、依存を踏まえて配分する。一つのrepositoryの負荷や故障で他の重要課題を飢餓させない。
- worker、repository、要求量が増えたときの処理量と外部I/Oの増加率を設計・検証する。

### 6. 判断と結果を実環境で検証可能にする

- 要求、判断、変更、失敗、再試行、外部状態の観測、Preview実績、Stable昇格の対応を追跡できるようにする。
- 品質保証を自動testだけに寄せない。対象リスクに応じて、契約検証、smoke、Previewでのdogfooding、Stableとの実測比較、停止・rollback・再開確認を組み合わせる。
- 完了、停止、復旧、昇格は自己申告や内部状態だけで決めず、利用者が観測する結果と外部副作用を含めて検証する。
- 失敗、縮退、未確認事項を成功履歴から隠さない。一方、検証のために秘密、過剰な個人情報、無制限のraw logを保存しない。

### 7. 手段を固定せず単純さを守る

- 特定のAI tool、provider、hosting、VCS、GitHub上の状態表現、現在の実装をプロダクトの本質にしない。
- 外部systemとの接続と副作用を明示的な境界に隔離し、交換可能にする。
- 新しい仕組みや補正を追加する前に、不要な状態、機能、同期、moduleを削除または置換できないか検討する。
- 外部systemの偶然の制約や現行実装の都合を、検証なしに恒久的なdomain ruleへ昇格させない。

## 優先順位と変更権限

- 大原則は、個別要求、計画、既存実装、互換性、効率、ループ自身の判断より優先する。
- 大原則を同時に満たせない、または満たしたことを検証できない場合は、不可逆な処理を始めず、完了ともせず、人間へ判断を求める。
- ループは大原則を自律的に変更、迂回、弱化、削除してはならない。問題を発見した場合は理由、影響、代案を人間へ提案する。
- 大原則の意味を変えるには、人間による対象差分への明示的な承認を必要とする。表現変更を装った弱化も同様に扱う。

## 大原則に含めないもの

GitHub Issue、Cloud Run、Firestore、command名、file path、API schema、test framework、worker数、
timeout秒数、retry回数など、保証を実現する交換可能な方式と調整値は、変更可能なproduct
specification、architecture、policy、runbookへ置く。
