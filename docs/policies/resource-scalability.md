# 有限資源とスケーラビリティのポリシー

## 目的と優先関係

CPU・メモリ・ディスク・ネットワーク・外部API・token・ログ・CI時間はすべて有限であり、データ件数・利用回数・並列数・実行時間は増加する前提で設計する。このポリシーはすべての変更に適用し、個別機能の利便性より優先する。性能を口実に正しさ・回復可能性・可読性・外部環境ポリシーを損なってはならない。[費用ポリシー](cost.md)・[テストポリシー](testing.md)・[検証ハーネスポリシー](validation-harness.md)とは同時に満たす。

## 設計時に明らかにすること（処理量モデル）

外部I/O・pagination・探索・retry・待機・並列処理を追加または変更する変更は、次を設計時に明らかにする。

1. 1操作・1周期・1対象・1workerあたりの処理回数・外部呼び出し回数。
2. 入力件数N・worker数Wに対する時間・空間・I/O量の**増加率**。
3. pagination・探索・retry・待機の**停止条件**と上限。
4. 同一データの再取得を避ける共有・集約取得・差分取得・早期終了・キャッシュの可否。
5. idle時・障害時・複数host時に負荷が増幅しないこと。

要求本文に性能要件が明記されていなくても、有限資源に関する妥当な非機能要件をAgentが自ら発見し、要求・計画・レビュー・完了判定へ含める。

## 全件取得・無制限paginationの扱い

一律禁止しない。必要性・想定規模・停止条件・代替案を宣言し、検証できる場合にのみ採用する。宣言は当該コード行の直前へ注釈として残す（書式は[運用文書](../operations/workload-budget.md)を参照）。宣言が無い全件取得・無制限paginationは、共通入口の静的検査で検出する。

## 安全弁は効率的な通常設計の代替にしない

rate limit・quota・timeout・メモリ上限などの安全弁はdefense in depthであり、「安全弁があるから合格」とは判定しない。通常経路そのものの呼び出し回数・増加率を検証対象にする。

## 外部アクセスの集約

外部I/Oは共通境界（このrepositoryでは`repo_api`・`comment_post`・`comment_patch`）へ集約し、ガード・計測・キャッシュ・retry規律を迂回する独自呼び出しを追加しにくくする。共通境界を迂回する必要がある場合は、その理由を注釈で宣言する。

## 例外の記録方法

コード上の注釈文法（[運用文書](../operations/workload-budget.md)を参照）と、plan段が出力する`agentic-loop:workload` recordの`exceptions`配列で記録する。既存実装に発見した無境界I/Oや同一データの重複取得は、その場での全面最適化を要求せず、`track=#N`で追跡Issueへ切り出してよい。

## 検証方法

呼び出し回数の上限test、入力規模を変えたfixtureによる増加率test、共通境界迂回・無境界paginationの静的検査を、共通入口（`devbox run --pure check`）から実行する。小規模fixtureで偶然通るだけの状態を合格としない。
