# テストポリシー

## 目的

このポリシーは、実際の利用方法に近い検証で要求の充足を保証しつつ、失敗箇所を迅速に特定できるテスト構成を定める。すべての変更に適用する。

## テストレベル

外部影響を伴わない要求は、原則としてエンドツーエンド（E2E）テストでカバーする。E2Eテストは公開された入力点から実行し、利用者が観測できる結果と主要な失敗経路を検証する。内部実装の詳細には不必要に依存しない。

次のような項目は単体テストで検証する。

- E2Eで網羅すると遅い、または原因を特定しにくい細かな分岐
- 境界値、異常値、組み合わせの多い入力
- 複雑な計算、変換、状態遷移その他のロジック

単体テストはE2Eテストの代替ではない。要求の主要な利用経路をE2Eで保証し、単体テストで必要な網羅性と問題の局所化を補う。

## 外部影響の分離

本番データの変更、外部への通知、課金、外部サービスのリソース作成・更新・削除などを外部影響とする。CIのテストからこれらの実操作を行わない。

外部影響との境界は、フェイク、スタブ、ローカルな一時環境、または副作用のない検証インターフェースに置き換える。その境界までのフローと、外部へ送る呼び出し内容を自動テストで検証する。実サービスとの結合の確認が必要な場合は、追加費用、データ破壊、通知、可用性への影響がない方法を個別に設計する。

## CIと実行条件

すべての自動テストはリポジトリ共通の検証入口から実行できなければならない。CIの採否と実行条件は[検証ハーネスポリシー](validation-harness.md)に従い、public repositoryではpushとpull requestでCIがその入口を実行する。このリポジトリの共通入口は、固定された開発環境で `make check` を呼び出す `devbox run --pure check` とする。

テストは毎回独立して実行でき、再実行可能で、実行順序や以前の実行結果に依存しないものとする。失敗時は検証した要求と差分を識別できる情報を出力する。

## flakyなtest

同一commit・同一固定環境で結果が不安定なtestをflakyとする。再実行は検知・診断目的に限定し、`passed`への昇格には使わない。最初の失敗ログと全試行結果を必ず保持する。

明示的な隔離（quarantine）は、対象・期限（最長14日）・責任者・修復Issueの4条件を宣言した場合に限り認め、対象のtest coverageを恒久的に失わない。期限切れや未修復の隔離entryは可視化し、放置しない。決定的に失敗するtest（再実行しても直らないもの）は隔離できない。詳細は[検証ハーネスポリシー](validation-harness.md)と[運用ドキュメント](../operations/flaky-tests.md)を参照。

## 変更時の完了条件

変更ごとに影響する要求と失敗リスクを特定し、必要なE2Eテストと単体テストを追加または更新する。テストを追加できない場合は、理由、代替の検証方法、残るリスクを変更の記録に明記する。

完了には、ローカルで共通の検証入口が成功し、検証ハーネスポリシーがCIを要求する場合はCIでも同じ入口が成功することを必須とする。
