Requirement capture time

The capture time is the instant the Requirement was recorded, taken once from the transaction that recorded it, so it is the same instant that transaction’s own event carries and it does not move if that transaction is retried. It is never the time this page was opened and never the time anything was read. A Requirement recorded before this field existed has no capture time: the response omits the field entirely and this page says so in words, because an empty value and a year-1 date would both read as a real instant. The ordering rule that keeps a waiting Requirement from being starved uses this value, and its guarantee is bounded: it is a true statement only while the spread between the capture times of competing Requirements stays inside a measured interval, and nothing in the running system bounds that spread today. That limit is recorded, not fixed here.

Why work is waiting

  • Loading…

The limit is not a control mode. It is recorded beside the Control Intent revision that declared it, and the seven modes keep their exact present meaning: a mode decides whether work may proceed at all, a limit decides how much may proceed at once. A revision that declares no limit leaves the limit alone, so an unrelated pause never silently resets it. Lowering the limit below the work already running revokes nothing: no lease is cancelled, no claim is dropped and no token is re-fenced, and the installation converges to the new limit as work finishes — the reading below will show it exhausted until it does. The waiting reasons are the scheduler’s own closed set, reported as it gave them, and this page invents none of its own. Whether capacity is exhausted is counted from capacity itself, not read off a waiting reason, so work can be waiting on a conflict while capacity remains. Reading this page decides nothing and changes nothing: it asks the scheduler what it would allocate from the state read in that one request, and never applies the answer. A limit shown as coming from the architecture design ceiling is one nobody chose; only a limit named with its control revision was chosen by an owner.

Provider version compatibility, and where work would go

Two separate relations are reported per Provider, and neither is collapsed into the other. The first is which Provider CLI versions this adapter declares support for. The second is which Loop versions carry that adapter contract. Both are declarations this repository owns, read from its own source; a version a CLI reports about itself is never the authority, and neither is a version printed inside a Provider response. Whether a declared range is actually true of a real CLI is established by nothing on this page.

A state shown as unknown means an input was absent, not that everything is fine. The observed Loop version is absent whenever this process was given no explicit release source root, and the version of the CLI on the Runner machine never reaches this control plane at all, so the CLI state stays unknown unless the Loop's own last invocation failed because the adapter could not parse what the CLI produced. Reading unknown as fine would be a mistake.

The last column is what a single declared decision function says now: nothing needs to move, or a proposed destination, or one reason the Loop is waiting. A proposed destination is a proposal an owner reads. Nothing in this repository carries it out, and reading this page moves no work and changes nothing.
